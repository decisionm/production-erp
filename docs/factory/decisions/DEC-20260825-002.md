Vendor is a CONFIGURATION master, and a purchase order selects a vendor from that configuration rather than inventing one. Three parts. (1) The vendor master lives on the Configuration Lifecycle Contract already in force for the other masters (DEC-20260817-002, which this does not replace): create, view, edit, activate/deactivate, archive, and hard delete only where the record is proven never-used and dependency-free. (2) A purchase order offers the ACTIVE configured vendors. Where the vendor a buyer needs is absent, an authorized user creates it in Configuration and then raises the order; the creation happens on the vendor master screen, not inline on the purchase order, so a vendor is never created as a side effect of getting an order out. (3) A vendor MAY be saved without an exact Tally ledger mapping, because the master must not be blocked waiting on Accounts - but a vendor whose Tally ledger is unmapped has its Tally Purchase Order posting WITHHELD and REFUSED, never posted against a guessed or approximately-matched ledger. That refusal is the rule DEC-20260812-002 already states for a vendor with no Tally identity; this decision re-affirms it for the configuration path and does not supersede or weaken it. One thing is expressly NOT decided here and remains open: PENDING Q53(c), whether a RETIRED vendor should also block a Tally-MIRROR purchase order (source: tally), stays unanswered, and the narrow behaviour pinned by the existing mirror test is unchanged by this decision.
