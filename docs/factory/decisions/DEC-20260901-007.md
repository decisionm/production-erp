Recording a production consumption line the run was NOT PLANNED ON requires consumption-substitute.manage, and that permission is held by ADMINISTRATOR AND PLANT MANAGER, and by nobody else by default. This resolves PENDING Q91. Accounts is deliberately NOT granted: booking what a machine ate is a floor act, not a books one. The SUPERVISOR role does not hold it, so the reason box alone is not the control - the completion drawer refuses the line and tells the supervisor to fetch an authorised person, and the Plant Manager is that person because they are on the floor when a material runs out. The second lever the question named - widening what counts as PLANNED in RunConsumableOptionsService::expectedItemIds() - was expressly NOT pulled: incomplete BOMs, packing mappings and dosing rows are the real reason an ordinary line reads as unplanned, and widening the planned set would hide that rather than fix it. The grant is made with givePermissionTo and never syncPermissions, following the carton-trace precedent, so the seeder re-running on every deploy only ever ADDS this one permission and never rewrites what an administrator configured through the Roles screen. SEPARATELY AND IN THE SAME BREATH, the added line now satisfies DEC-20260901-004 in full: it carries substitutes_item_id, the item it stood in for, beside the reason and the author it already carried. That column is NULLABLE and is not required on every added line, because an added line is not always a substitution - a run may book a consumable that replaced nothing, and forcing a name there would make somebody invent a factory value. Every added line still requires its reason; a line that IS a substitution also names what it replaced, and it does so with the same column and the same predicate store_issue_lines uses, so the storekeeper's handover and the machine's actual consumption answer the question identically. This is a WHO-MAY-RECORD rule and remains expressly NOT the approver-above-the-recorder that DEC-20260901-004 leaves undecided and unbuilt; no approval workflow exists.
