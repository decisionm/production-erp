## Summary

1. Material reaches the floor through TWO code paths that never meet in the stock ledger: the floor's day-bin bag scan writes NO stock movement (an operational `day_bin_movements` Load row plus the resin cost pool), while the Store Issue — which already carries its own bag scan at the handover — is a signed transfer pair into the Production/WIP warehouse row that writes no day-bin row and no pool entry; a batch completion decides its consumption warehouse per line as WIP → day-bin warehouse → raw-material store. Since 02-Sep `DEC-20260902-002` makes the Store's scan the only scan; the code still runs the floor scan (`Q94` blocks the change).
2. Incoming Quality is one inspection per GRN line, whole-line only, at whole-bag granularity: accepted bags flip `waiting_qc → in_store`, rejected bags flip to `rejected_qc` and their kilograms leave through a `Rejections Out RJO-…` issue; nothing reaches Tally for a rejection, and that is recorded as open rather than decided.
3. There is no finished-goods "quality checklist" model anywhere in the code: the FG quality stage is a reviewed/ok/rejected COUNT gated on `quality.manage` and four-eyes, sitting as a precondition of Plant Manager approval, not as a status of its own.
4. The Tally Stock Journal is created at ACCOUNTANT APPROVAL (one voucher per production_date + shift, `SJ-{Ymd}-S{shift}`), and RELEASED to the agent only after the shift's `end_time` has passed plus a 15-minute idle hold, or by Release now / Sync Now — shift end creates nothing by itself.
5. Every seeded item is category NULL, no migration writes `Other`, and no requisition or PO code path refuses an item on category; the eligibility rule (Q59a) is undecided and the 02-Sep owner statement in chapter 01 is REQUIRED, not yet a record.

## 1. How material reaches the production floor — physically and in the ledger

### 1a. Flow A — the centralised day-bin bag scan

**What the decisions say.** The floor's only resin flow is the centralised day bin: one crane-fed loading point piped to all ten machines; consumption is derived per batch at completion; bag-to-batch identity is never claimed — `DEC-20260807-006`, whose load-time clause ("the supervisor scans the inward-generated bag barcode at load") was SUPERSEDED on 02-Sep-2026 by `DEC-20260902-002`: the Store scans each bag once at the Store Issue, the issue moves the material into Production/WIP, and the bag reaches the day-bin load with NO second scan by the floor; every other clause of `DEC-20260807-006` is restated in the new record (`docs/factory/CURRENT-DECISIONS.md:14,152`). A scan is a pour record, not Tally consumption; a bag belongs to no machine and no batch — `FC-01` (`docs/factory/FACTORY-CONSTITUTION.md:12-25`). The bin is never weighed, so its balance is Σ loads − Σ calculated consumption and is an estimate that drifts — `DEC-20260807-007`. **The code below still implements the superseded clause** — the commit that recorded `DEC-20260902-002` (ee92642) changed four knowledge files and no code, and `Q94` records that the code change cannot be designed until `Q94(a)` is answered.

**Route and gate.** `POST /api/v1/production/day-bin/load-bag` → `FactoryDayBinController::loadBag` — `backend/routes/api.php:1336`. It sits inside the `traceability` middleware group (`backend/routes/api.php:1307`), which 404s the whole surface unless `production.traceability_enabled` is on (`backend/config/production.php:426`, default `true`). The production group requires `production.manage` for a POST (`backend/routes/api.php:994`; `backend/app/Http/Middleware/EnsureModulePermission.php:35-43`).

**Controller.** `backend/app/Modules/Production/Http/Controllers/FactoryDayBinController.php:112-139`. The controller's own comment states "a load no longer moves stock" (`:126-130`).

**Service — what a scan writes, inside one transaction** (`backend/app/Modules/Production/Services/FactoryDayBinService.php:182-300`):
- refuses when no day-bin warehouse is configured (`:189-194`); the setting key is `production_day_bin_warehouse_id` (`:77`), resolved by `warehouse()` (`:123-133`);
- resolves barcode → bag → lot → kg through the shared scanner `MaterialBagIssueResolver` (`:204-215`), which carries the incoming-QC hold refusal for a `waiting_qc` bag (`backend/app/Modules/Inventory/Services/IncomingQcHold.php:13-16`);
- pours the bag: a full load leaves the bag `consumed`, a partial load leaves it `in_store` holding its remainder (`:224`; docblock `:169-171`);
- **writes NO stock movement** — "A scan is an OPERATIONAL record, not an accounting one" (`:232-248`); pinned by `backend/tests/Feature/FactoryDayBinBagLoadTest.php:142` (`A scan must write no stock movement at all`) and the zero-movement asserts at `:171,192,216,281,299,319,340,357`;
- writes a `day_bin_movements` row of type `load` with `work_center_id` NULL and no `shift_production_entry_id` (`:255-271`; enum `backend/app/Modules/Production/Models/Enums/DayBinMovementType.php:7-9`; table `backend/database/migrations/2026_07_28_200003_create_day_bin_movements_table.php:18-36`);
- folds the bag's lot rate into the common resin pool — `ResinPoolService::fold` (`:281`). This is the ONLY `fold()` caller in the application (grep of `backend/app/`: `FactoryDayBinService.php:281` only; `StoreIssueService.php` and `MaterialRequestService.php` contain zero pool calls) — the fact `Q55(b)` records.

**Where the day-bin flow is read.** Read-only routes: `GET production/factory-day-bin` (`backend/routes/api.php:1011`), `factory-day-bin/raw-materials` (`:1015`), `machine-resin` = the factory-wide common-input estimate (`:1030`), `day-bin/movements` and `day-bin/consumption` (`:1328-1329`), per-machine and per-entry state (`:1340-1341`), `bin-bay/availability` (`:1351`). `DayBinController` is read-only since Phase 7.5 — the three machine-stamped write doors (`day-bin/load`, `return`, `count`) are retired (`backend/app/Modules/Production/Http/Controllers/DayBinController.php:15-34`); `BinBayController` is read-only, the Bin Bay page and `bin-bay/load` having gone with `DEC-20260807-006` (`backend/app/Modules/Production/Http/Controllers/BinBayController.php:10-21`). `DayBinLedgerService` is a historical-only reader whose two live writers are the scan and the closing counts written at completion/handover (`backend/app/Modules/Production/Services/DayBinLedgerService.php:4-27`); those closing counts are `ShiftProductionEntryService::recordClosingDayBin` (`backend/app/Modules/Production/Services/ShiftProductionEntryService.php:779,1624,3608-3620`), called from `completeBatch` and `handover`.

**Frontend.** `/production/day-bin` is still routed (`frontend/src/app/App.tsx:273`) but has no nav entry; the layout comment explains the route stays because the page hosts the only writer of the day-bin warehouse setting and the scan is the sole resin-pricing inflow, and that the floor scans from the Shift Floor page (`frontend/src/app/AppLayout.tsx:259-275`).

**Tables the day-bin flow touches.** `day_bin_movements` (above); `material_bags.status/remaining_kg` (pour); the resin pool (`ResinPoolBalance` model, `backend/app/Modules/Production/Models/ResinPoolBalance.php`); and at completion `batch_resin_allocations` — the bag-cost analytic layer that "SITS BESIDE THE STOCK LEDGER, NEVER INSIDE IT" (`backend/database/migrations/2026_08_02_000001_create_batch_resin_allocations_table.php:8-20`), written by `BagCostAllocationService::allocate` from `completeBatch` (`ShiftProductionEntryService.php:1000-1010`). None of these is a `stock_movements` / `stock_balances` write.

### 1b. Flow B — the Store Issue into Production/WIP

**What the decisions say.** One physical Store; raw material, packing, WIP and finished goods are told apart by category, state or INTERNAL LOCATION, and the Production/WIP internal location — the warehouse row coded `WIP` — must remain resolvable — `DEC-20260830-002` (supersedes `DEC-20260817-001`). The evening return is partial or full, must name its Store Issue where one exists, and the next request nets against usable WIP stock — `DEC-20260831-005`; a Store Issue's claim lasts while returnable quantity remains, whatever its status — `DEC-20260831-008`; a full return is not mandatory — `DEC-20260901-001`; substitution is two lines with reason — `DEC-20260901-004`.

**Routes.** Under `Route::prefix('inventory')->middleware('module:inventory')` (`backend/routes/api.php:172`): `store-issues/outstanding`, `/trace`, index, show, `POST store-issues`, `/returns`, `/complete`, `/cancel` (`:268-275`); `production-returns/returnable` and `POST production-returns` (`:287-288`); `POST damaged-finished-goods` (`:306`); the handover bag scan `POST store-issues/{id}/bag-scans` inside the `traceability` group (`:323`).

**Service — what an issue writes.** `StoreIssueService::issue` (`backend/app/Modules/Inventory/Services/StoreIssueService.php:91-190`) resolves Production/WIP first and refuses with a 422 when it cannot (`:95`; `ProductionWipLocationResolver::warehouseOrFail`, `backend/app/Modules/Inventory/Services/ProductionWipLocationResolver.php:143-152`, message `:50-52`). Each line is a signed TRANSFER pair from the store to WIP with purpose `issue_to_production` (`:1186-1187,1201`; also `:271-272,324` for the bag-scan line); the class docblock states this is the three-state design Store Stock → Issued to Production → Consumed (`:4-30`). Status enum: `issued`, `partially_returned`, `returned`, `completed`, `cancelled` (`backend/app/Modules/Inventory/Models/Enums/StoreIssueStatus.php:20-41`). A typed line is refused above an incoming-QC hold (`:1238-1280`) and an item must be `is_production_input` (`backend/app/Modules/Inventory/Http/Requests/StoreStoreIssueRequest.php:283-293`; material requests likewise, `backend/app/Modules/Inventory/Http/Requests/StoreMaterialRequestRequest.php:50-53`).

**WIP resolver precedence.** app setting `production_wip_warehouse_id`, else the single warehouse whose code is exactly `WIP`, else null → 422 (`ProductionWipLocationResolver.php:45-77`); `is_active` is deliberately NOT filtered (`:27-35`); nothing creates or reactivates a row (`:37-40`).

**Returns.** `StoreIssueService::returnUnused` writes the mirror pair purpose `return_from_production` (`:368-480`, `:453`); `ProductionReturnService::record` is the one door for attributed and unattributed returns (`backend/app/Modules/Inventory/Services/ProductionReturnService.php:224-330`, purpose `:320`), refusing an unattributed return while an open issue stands on that material (`:482-516`, docblock `:44-60`). A `damaged` line goes to the quality-hold location and the caller's destination is not consulted (`:668-675`); `ReturnedQualityState` is `good | damaged` (`backend/app/Modules/Inventory/Models/Enums/ReturnedQualityState.php:55-60`).

**The Store's bag scan at the handover — already in code.** Chapter 02 lists "whether the current Store Issue screen already scans bags" as verification pending. It does. `POST inventory/store-issues/{id}/bag-scans` (`backend/routes/api.php:323`, traceability-gated) → `StoreIssueService::scanBag` (`StoreIssueService.php:241-340`): resolves the barcode through the same `MaterialBagIssueResolver` the floor uses, so a `waiting_qc` or `rejected_qc` bag is refused here too (`:225-228,254-255`); pours the bag (`:279`); adds the kg to one issue line per (material, source store), creating it against Production/WIP if absent (`:262-276,301`); credits the material-request line (`:313-315`); writes the stock TRANSFER store → WIP with purpose `issue_to_production` (`:317-325`); and records a `store_issue_bag_scans` row — bag, lot, kg, issued by, received by, when, request line — which is the last link the ERP claims about a bag (`:327-338`; `backend/app/Modules/Inventory/Models/StoreIssueBagScan.php:8-24`). It writes NO `day_bin_movements` row and NO resin-pool entry (grep of `StoreIssueService.php` for `DayBin|ledger->|ResinPool|pool->` finds none; `backend/tests/Feature/Inventory/StoreIssueBagScanTest.php::test_the_scan_never_writes_a_day_bin_row`). The Store ↔ Production screen offers it as a "Scan the bag barcode…" input on the handover panel (`frontend/src/features/material-flow/components/HandoverPanel.tsx:161-163`; `frontend/src/features/material-flow/api.ts:122-124`).

**Purposes in the ledger.** `issue_to_production`, `return_from_production`, `consumption`, `output`, `scrap`, `quality_release` — `backend/app/Modules/Inventory/Models/Enums/StockMovementPurpose.php:40,47,50,53,79,103`.

### 1c. How a completion decides where consumption comes from

`ShiftProductionEntryService::completeBatch` (`backend/app/Modules/Production/Services/ShiftProductionEntryService.php:759-1010`): for every `material_consumptions` line the warehouse is the client's `warehouse_id` if sent, else `FactoryWarehouseResolver::consumptionSourceOrFail` (`:886-890`); the issue is written with purpose `consumption` and `allowNegative` from `production.stock.allow_negative_on_completion` (`:913-924`; `backend/config/production.php:313-314`, default `true`); a shortfall is frozen on `config_snapshot.stock_shortfalls` with a WIP-specific `basis` sentence and the completion is NOT refused (`:926-997`). Whether the factory would rather refuse is recorded as an owner question (`:970-975`; `Q54(e)`).

`FactoryWarehouseResolver::consumptionSource(int $itemId)` (`backend/app/Modules/Production/Services/FactoryWarehouseResolver.php:175-242`), in order:
1. **Production/WIP** when `productionWipIsInPlay`: the WIP row holds a NON-ZERO balance of the item (negative included) OR an open Store Issue still has quantity standing in WIP (`:229-233,390-399`; `StoreIssueService::hasMaterialStandingInProduction`, `StoreIssueService.php:740-753`). The old second condition "a store issue put it there" was removed under `DEC-20260831-009` (`:183-199`); pinned by `backend/tests/Feature/Inventory/WipAvailableWithoutAStoreIssueTest.php`.
2. **The day-bin warehouse** when it holds a POSITIVE balance of the item (`:235-239,372-379`). `dayBin()` is `FactoryDayBinService::warehouse()` else the sole active Tally-linked warehouse (`:154-157,361-370`).
3. **The raw-material warehouse**: the app setting else the sole active Tally-linked warehouse (`:97-100,241`).

`consumptionSource` is item-aware but has no packing-material branch: the Packing Material Store role (`:129-132`, setting only, no fallback) is consumed by the voucher payload and its preview, not by the stock ledger (`backend/app/Modules/TallySync/Services/TallySyncService.php:893,1281-1284`; `backend/app/Modules/TallySync/Services/VoucherPreviewService.php:75,292`).

**Does the day-bin flow feed Production/WIP?** No. A scan writes no stock movement (§1a), so the WIP balance and the `hasMaterialStandingInProduction` read are unaffected by scanning; the day-bin warehouse branch fires only if that warehouse row holds a positive balance put there by some other movement. `Q55(a)` records that when `production_day_bin_warehouse_id` is unset the branch is a behavioural no-op (both sides fall through to the same sole Tally-linked row) and that nobody has read the live value (`docs/factory/PENDING-OWNER-QUESTIONS.md:1229-1238`). This note does not assert the live value. The two flows meet only at completion: the ledger warehouse comes from `consumptionSource`, while the resin COST comes from the day-bin Load layers through `BagCostAllocationService` (`ShiftProductionEntryService.php:1000-1010`) — the store-issue flow prices nothing (`Q55(b)`). The converse also holds: the Store's handover scan feeds only the stock ledger, so under `DEC-20260902-002` (no floor scan) the common-input estimate (`FactoryDayBinService::commonResinEstimate`, which sums `load` rows, `FactoryDayBinService.php:599-620`), the resin pool and `batch_resin_allocations` would receive no inflow at all unless the Store Issue's scan starts writing them — which is exactly what `Q94(a)` asks (`docs/factory/PENDING-OWNER-QUESTIONS.md:2684-2703`).

**The completion dropdown.** `RunConsumableOptionsService` (`backend/app/Modules/Production/Services/RunConsumableOptionsService.php`): EXPECTED = BOM lines, resolved resin/masterbatch, the standard's packing, every packing-mapping and dosing item, and what this product was made with before (`:93-177`); ALLOWED = every active item except `finished_good` and the product itself, plus EXPECTED (`:78,184-200`); held-for-QC unplanned materials are not offered (`:207-254`). A line outside EXPECTED is an ADDED line requiring a reason, `substitutes_item_id` optional, and `consumption-substitute.manage` (`DEC-20260901-007`; `backend/app/Modules/Production/Http/Requests/CompleteBatchRequest.php:127-134`).

## 2. What Incoming Quality does today

### 2a. GRN → `waiting_qc`

`GoodsReceiptService::create` (`backend/app/Modules/Procurement/Services/GoodsReceiptService.php:247-431`) books the arrival as a stock receipt with purpose `receipt` (`:346-355`) and, per lot, calls `TraceabilityService::createLot` (`:366-367`). A bag born on a GRN is created `waiting_qc`; a lot created outside a GRN (opening-stock backfill) is `in_store` (`backend/app/Modules/Inventory/Services/TraceabilityService.php:171-187`). A lots block is refused for any item not measured in kg (`GoodsReceiptService.php:550-553`) and refused outright when traceability is off (`:531-536`); weighed arrivals must carry their bags (`DEC-20260831-010`; `backend/tests/Feature/Inventory/EveryWeighedArrivalIsCountedTest.php`). Bag statuses: `in_store`, `in_day_bin`, `consumed`, `returned`, `waiting_qc`, `rejected_qc` (`backend/app/Modules/Inventory/Models/Enums/MaterialBagStatus.php:7-18`). GRN posts no Tally Receipt Note (`DEC-20260830-001`).

### 2b. The hold on issuance

The hold is enforced at the balance: `StockMovementService::decrementBalance` locks the item's `waiting_qc` bags in that store, subtracts their `remaining_kg`, and refuses any outflow above the remainder — and the hold OUTRANKS `allowNegative` (`backend/app/Modules/Inventory/Services/StockMovementService.php:906-990`, refusal `:969-980`; `IncomingQcHold::lockAndSum/available`, `IncomingQcHold.php:83-113`). Every door reaches it: generic issue, transfer, store issue, shift completion, work order, delivery (`StockMovementService.php:915-926`). The single exception is `recordIncomingQcRejectionIssue`, which passes `honourIncomingQcHold: false` and is the one caller the inspection uses (`:167-183`). Pinned by `backend/tests/Feature/Inventory/StockOutflowQcHoldTest.php` (14 tests, including `a_shift_completion_cannot_consume_material_waiting_for_incoming_qc`, `a_hold_outranks_allow_negative`, `the_rejection_door_is_narrow_and_has_exactly_one_caller`). Records: `DEC-20260825-001`, `DEC-20260831-011` (every arrival waits for QA; counted materials create no bags and so are not held).

### 2c. The inspection

Route `quality/incoming-inspections` (index, store) under `module:quality` (`backend/routes/api.php:768-769`): GET needs `quality.view` or `.manage`, POST needs `quality.manage` (`EnsureModulePermission.php:35-43`). Request fields: `goods_receipt_note_line_id`, `inspected_quantity`, `accepted_quantity`, `rejected_quantity`, `inspection_date`, `notes` (`backend/app/Modules/Quality/Http/Requests/StoreIncomingInspectionRequest.php:17-30`).

`IncomingInspectionService::create` (`backend/app/Modules/Quality/Services/IncomingInspectionService.php:89-158`):
- one inspection per GRN line, a second is refused (`:101-105`);
- inspected ≤ received (`:111`); accepted + rejected = inspected (`:115`); inspected must equal the whole line — partial inspection is refused (`:126-128`; `backend/tests/Feature/Quality/IncomingInspectionCoverageTest.php`);
- result `pass` (rejected = 0), `fail` (accepted = 0), else `partial` (`:130-134`; `backend/app/Modules/Quality/Models/Enums/InspectionResult.php:5-10`);
- `dispositionBags` (`:181-304`): bags are taken newest-first, whole bags whose kg fit the rejected figure flip to `rejected_qc` (`:237-246`), everything else flips to `in_store` (`:255-263`); a bag the rejection ends INSIDE stays `waiting_qc` with a note, because splitting one bag's kilograms is "an OPEN OWNER DECISION" (`:166-169,247-252,300`);
- the rejected kilograms leave stock through `recordIncomingQcRejectionIssue` with reference `Rejections Out RJO-{GRN tracking or GRN{id}}-L{line id}` and the note "awaiting the Rejections Out voucher decision; no Tally entry is created here" (`:265-292`);
- a line with no bags records the rejection in `bag_disposition_note` and moves NO stock (`:195-229`).

Model fields: `rejections_out_reference`, `bag_disposition_note` beside the three quantities and the result (`backend/app/Modules/Quality/Models/IncomingInspection.php:14-18`).

### 2d. What "Rejections Out" issues, and what reaches Tally

"Rejections Out" is an ordinary ERP stock ISSUE against the GRN's warehouse for the summed `remaining_kg` of the bags flipped to `rejected_qc` (`IncomingInspectionService.php:284-292`). **Nothing reaches Tally for a rejection**: the code says so in two places (`:172-174,290`) and the records leave it expressly open — `DEC-20260825-001` ("what Tally should receive when material is rejected at QA (an accepted-only Receipt Note, or a full Receipt Note plus a separate rejection voucher)"), `DEC-20260830-001` ("Expressly NOT decided here and still open for Accounts"), `DEC-20260901-003` and `DEC-20260901-006` (the sibling clauses for scrapped returns and scrapped finished goods).

### 2e. The quality-hold location (QC-HOLD)

A second, different mechanism: `QualityHoldLocationResolver` resolves the app setting `quality_hold_warehouse_id`, else the single warehouse coded `QC-HOLD`, else null — and null REFUSES, never falls back (`backend/app/Modules/Inventory/Services/QualityHoldLocationResolver.php:35-53,64-129`). It holds QUANTITIES in a location, not bags, and deliberately does not reuse `IncomingQcHold` (`backend/app/Modules/Inventory/Services/ReturnedMaterialQualityService.php:46-50`). Doors in: a `damaged` production return (`ProductionReturnService.php:668-675`) and a damaged finished good reported by the Store (`backend/app/Modules/Inventory/Services/DamagedFinishedGoodService.php:59-155`, finished goods only `:110`). Doors out, both under `module:quality` (`backend/routes/api.php:807-809`): `confirm-damage` = an issue with purpose `scrap` (`ReturnedMaterialQualityService.php:103-123`), `release` = a transfer with purpose `quality_release` to a store that is not the hold (`:131-170`). Neither posts to Tally (`:39-43`). Records: `DEC-20260901-003`, `DEC-20260901-006`, `DEC-20260901-002`. Tests: `backend/tests/Feature/Inventory/DamagedReturnReachesQualityTest.php`, `DamagedFinishedGoodsReachScrapTest.php`.

## 3. Finished-goods quality stage and Product Configuration standards

### 3a. There is no checklist

A grep of `backend/app` and `frontend/src` for `checklist` returns no file. The finished-goods quality stage is a COUNT, not a checklist: the request takes `reviewed_nos`, `ok_nos`, `rejected_nos` (whole bottles) and an optional `note`, and refuses unless reviewed = ok + rejected and rejected ≤ produced (`backend/app/Modules/Quality/Http/Requests/StoreBatchQualityCheckRequest.php:40-43,58-69,82-90`).

### 3b. Exact status strings and the chain

- Batch lifecycle `batch_status`: `in_progress`, `completed`, `cancelled` (`backend/app/Modules/Production/Models/Enums/BatchStatus.php:7-20`).
- Approval chain `status`: `pending` → `pm_approved` → `approved` → `synced` | `failed`; `rejected` from either pre-approval stage; `accountant_approved` retained but never written (`backend/app/Modules/Production/Models/Enums/ShiftProductionEntryStatus.php:22-31`, docblock `:6-20`).
- The quality stage is NOT a status: it is `quality_checked_at` on the entry, a precondition of `pmApprove` (`ShiftProductionEntryService.php:2637-2668`), switchable by `production.approvals.quality_stage_enabled` (`backend/config/production.php:174`, default `true`; refused at the endpoint when off, `ShiftProductionEntryService.php:1924-1940`).
- Transitions: `completeBatch` sets `batch_status=completed`, `status=pending`, `completed_by` (`:847-856`); `recordQualityCheck` writes `quality_reviewed_nos/ok_nos/rejected_nos/checked_by/checked_at/note` and nets `quantity_produced` down (`:1998-2022`); `pmApprove` → `pm_approved` with `plant_manager_signed_by/at` (`:2664-2667`); `accountantApprove` → `approved` with `accountant_signed_by/at`, `approved_by/at`, then fires `ShiftProductionEntryApproved` (`:2775-2784`); `markSynced`/`markSyncFailed` → `synced`/`failed` (`:3001-3016`); `reject` from `pending|pm_approved|accountant_approved` → `rejected` (`:2966-2976`); `returnToProduction` reverses the check's stock effects and hands the batch back to the floor (`:2248`). A carton scan renders a `rejected` batch as `quality_rejected` (`backend/app/Modules/Production/Models/ShiftProductionEntry.php:357`).

### 3d. What the quality check does to stock

Rejected pieces are ISSUED out of the batch's finished-goods warehouse (`QC #{id}`, `allowNegative` from the completion setting) (`ShiftProductionEntryService.php:2097-2110`), and their mass (pieces × the run's frozen unit weight) is RECEIVED as scrap at the scrap item's own running average (`:2137-2152`); a `ShiftScrap` line of type `rejected_finished_good` is created (`:2160-2164`). The scrap item is resolved by `ScrapItemResolver` from `production.scrap.rejected_item_sku`, default `Pet Scrap`, exact SKU then exact name, never a pattern (`backend/config/production.php:248-267`; `backend/app/Modules/Inventory/Services/ScrapItemResolver.php:4-30`). When it does not resolve or no unit weight resolved, the receipt is skipped and a `quality_scrap_note` is written onto the entry (`:2117-2135,2170-2178`). Records: `FC-02`, `DEC-20260805-001`.

- `MasterbatchDosing`: `masterbatch_item_id, product_item_id (null = every product), grams_per_bottle` — a prefill only (`backend/app/Modules/Production/Models/MasterbatchDosing.php:4-16`; `DEC-20260806-003`, `DEC-20260806-010`).

The Factory Rules tab's ten rows are read by no rule — `FactorySetting::READ_BY_SOFTWARE` is `masterbatch_colour_map` only (`backend/app/Modules/Production/Models/FactorySetting.php:26-34`; `Q93`).

### 3f. What Start Batch and completion validate against the standards

**At Start Batch** (`ShiftProductionEntryService::startBatch`, `:412-640`): the finished-goods warehouse is resolved server-side (`:426-428`); the standard and packaging are resolved (`:480-481`; a packaging that is a separate product is refused, `:509`); the approved machine configuration is resolved (`:532`); the readiness gate runs (`:546-556`, `ProductNotReadyException`); effective cycle time and cavities are resolved within configured limits and with a reason (`:562-578`); the snapshot precedence is configuration → standard → item master (`:636-637`; `DEC-20260805-005`).

`ProductReadinessService::assess` checks `item_active, uom, weight, cycle_time, cavities, packing (nos_per_box), colour, tally_item, tally_godown, machine_active` (`backend/app/Modules/Production/Services/ProductReadinessService.php:49-60,273-350`), reading configuration → standard → item (`:301-315`). A missing consumption recipe is deliberately NOT a finding (`:317-326`); a `LOCAL-` fixture skips the Tally-item check (`:335-339`). Severity per check is config: every check `block` except `colour` = `warn` (`backend/config/production.php:555-565`) — but the master switch `production.readiness.enforced` defaults to `false`, under which every blocking finding is reported as a warning and nothing refuses (`:553`; `ProductReadinessService.php:247-251`; `backend/tests/Feature/ProductReadinessGateTest.php::test_the_shipped_default_is_watch_only`). So, as shipped: a product with no weight, cycle time, cavities, packing or Tally item PROCEEDS with named warnings; a wrong-product packaging id or an unresolvable finished-goods warehouse REFUSES regardless.

**At completion**: the unit weight is the run's frozen figure, never the item master's current column (`:781-787`); every material line must be in `allowedItemIds` and an unplanned line needs a reason and the added-line permission (§1c); consumption variance and unaccounted-kg bands are advisory unless `variance_blocking_pct` / `unaccounted_blocking_kg` are set (`backend/config/production.php:93-98`; `ShiftProductionEntryService.php:2758-2772`); the Tally-postability gate at accountant approval is `require_postable_voucher`, default `false` (`backend/config/production.php:209`; `:2714-2756`).

Open on this section: whether a standard must keep exactly one default packaging — `Q45`; which rejection figure the CEC sheet carries — `Q47`; the factory-rules enforcement — `Q93`; whether a QC checker holding Plant Manager may approve their own check — config comment only, no Q id (see "Not found").

## 4. How and when the Tally Stock Journal is posted

**What creates a voucher.** Accountant approval, and only that: `accountantApprove` fires `ShiftProductionEntryApproved` (`ShiftProductionEntryService.php:2782-2784`); `TallySyncEventServiceProvider` listens and calls `TallySyncService::enqueueShiftProductionEntry` (`backend/app/Modules/TallySync/Providers/TallySyncEventServiceProvider.php:150-152`). A `LOCAL-` fixture product is skipped with a log line (`backend/app/Modules/TallySync/Services/TallySyncService.php:612-633`). Under `tally-sync.voucher_granularity = 'shift'` (`backend/config/tally-sync.php:31`, default) `enqueueShiftVoucher` merges the entry into ONE pending Stock Journal per `(production_date, shift)`, numbered `SJ-{Ymd}-S{shift_id}`, with `-2/-3` follow-ups once the first has synced or failed; membership is `shift_production_entries.tally_sync_entry_id` (`TallySyncService.php:1063-1100`). Vouchers contain only approved entries; a batch stuck in QA does not hold its shift's voucher — `DEC-20260807-012`. Shift end creates nothing: no code path enqueues on a shift boundary.

**What releases a voucher to the agent.** `ShiftVoucherReleaseGate::hold` withholds a pending, undelivered, unreleased SHIFT voucher until (a) the shift's `end_time` has passed for the voucher's production date — read from `shifts.end_time` in the factory timezone, +1 day for an overnight shift — AND (b) at least `tally-sync.release_idle_minutes` (default 15) since `last_merged_at` (`backend/app/Modules/TallySync/Services/ShiftVoucherReleaseGate.php:56-138`; `backend/config/tally-sync.php:48,65`). `TallySyncService::pending` — the agent's `GET tally-sync/pending` (`backend/routes/api.php:895`) — rejects withheld entries (`TallySyncService.php:1355-1384`). Records: `DEC-20260807-010` (per shift, chosen over the accountant's per-DAY practice), `DEC-20260807-011` (release rule), `DEC-20260807-014` (the flip executed 07-Aug). Tests: `backend/tests/Feature/TallySync/ShiftVoucherGranularityTest.php`, `ShiftVoucherReleaseGateTest.php`, `VoucherPostedOnceTest.php`, `BatchVoucherShapeTest.php`, `ProductionStockJournalMatchesRealTallyTest.php`.

**Overrides.** Per voucher: `POST tally-sync/entries/{id}/release` (`backend/routes/api.php:855`) → `releaseNow` stamps `released_at/by` (`TallySyncService.php:1766-1790`). Queue-wide: `POST tally-sync/sync-now` (`:866`) → `requestSyncNow` frees every withheld pending row in one locked transaction, a repeat click is a no-op on the queue but every press is audited (`:1812-1870`); gated on `tally-sync.manage` plus `SyncNowAuthority::PERMISSIONS = ['finance.view','finance.manage']` (`backend/app/Modules/TallySync/Services/SyncNowAuthority.php:37-42`; controller `backend/app/Modules/TallySync/Http/Controllers/TallySyncController.php:129`) — `DEC-20260825-002`. Only the local agent posts; it acks/fails through `entries/{id}/ack|fail` (`backend/routes/api.php:896-897`) and the status fans back onto the member entries (`TallySyncEventServiceProvider.php:158-175`).

**Voucher shape** is validated against the factory's own export in `docs/tally-sync/2026-09-01-production-journal-validation.md` (FC-02/03/04 and one godown confirmed; three non-production journals held under `Q92`). Open: a clock-based cadence instead of continuous polling — `Q65`.
