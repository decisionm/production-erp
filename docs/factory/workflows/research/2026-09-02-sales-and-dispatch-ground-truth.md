## Summary

1. The factory act is the ERP's end to end — customer, order, hold, production request, Quality sign-off, dispatch — and the accounting integration is INBOUND in the shipped default: both outbound flags (`tally-sync.delivery_notes_enabled`, `tally-sync.sales_invoices_enabled`) default OFF, but the Delivery Note and Sales voucher builders, their listeners and the agent-side XML builders are all still in the tree behind two `.env` switches whose live values this note did not read. The ERP's OWN invoice document (`INV-{id}`, draft → issued, never paid) also still exists and is still raised by Sales after the Store dispatches.
2. A hold is a `stock_reservations` row and never a stock movement; it is refused under a balance lock above free stock or above what the line still owes; it is released or re-pointed only with a typed reason; a shortfall goes to the floor as a `production_requests` row capped at the true shortfall; "covered" is delivered plus the OUTSTANDING part of live holds, exactly as `DEC-20260902-032` confirms. The queue is ordered by a dense manual `priority` (raised order, re-numbered by a reason-less reorder) — the promised-date sort, sticky manual position, recorded reason and "moved" flag of `DEC-20260902-031` are NOT built.
3. "Internal Quality approval" is a stamp on the sales-order LINE (`quality_approved_at/by/quantity/note`) written under `quality.manage` only when the line is fully held; it caps dispatch at the approved quantity, cannot be skipped by any flag, and is revocable until anything ships. It checks NOTHING about the batch the goods came from: the only batch-quality gate is the carton scan's refusal of a `rejected` batch, and a typed delivery has no batch check at all. Chapter 3's step 4 ("have passed batch Quality") and step 5 ("only the approved cartons") describe a link the code does not hold.
4. The dispatch is `POST /sales/deliveries` under `module:inventory` — the Store's own `inventory.manage`, with `sales.manage` refused — and writes ONE stock issue with purpose `dispatch` from whatever warehouse the Store named, spends holds only where they sit (the finished-goods warehouse), and moves the order to `partially_delivered` or `completed`. Partial dispatch is allowed within the ordered remainder and the approved remainder. A recorded delivery has no cancel, amend or reverse path.
5. The Tally Sales Invoice import is an artisan command over an exported XML file (`tally:import-sales-invoices`, dry run by default) with no route, no screen and no workflow around it; the key is `customers.tally_ledger_name` + `sales_orders.customer_po_reference`; an unmatched voucher is stored with a named reason and no order is ever created. A match writes `tally_sales_invoices.sales_order_id` and nothing else: `sales_orders.status` is untouched by design, the resulting `tally_invoice` block on the order API is rendered by no screen, and the IRN / e-way details in the XML are read past and not stored — while `DEC-20260831-012` says the ERP will "UPDATE the ERP Sales Order's status from that match".

## 1. Customer master

### 1a. What a customer record holds

`customers`: `code` (unique), `name`, `email`, `phone`, `address`, `is_active` (default true), timestamps, soft delete (`backend/database/migrations/2026_07_18_163621_create_customers_table.php:11-21`); `gstin` (15 chars) and `state_code` (2 chars) added later (`backend/database/migrations/2026_07_18_173133_add_gst_fields_to_customers_table.php:11-14`); `created_by` / `updated_by` audit stamps, nullable, no backfill (`backend/database/migrations/2026_08_20_120000_add_audit_stamps_to_vendors_and_customers.php:44-60`); and the Tally identity `tally_ledger_guid` + `tally_ledger_name`, nullable, no unique index, deliberately NOT a foreign key to the `ledgers` mirror (`backend/database/migrations/2026_08_26_110000_add_tally_ledger_link_to_customers.php:26-36,49-52`).

The model's fillable set is `code, name, email, phone, address, gstin, state_code, is_active`; the two ledger columns are NOT fillable, so no form or request can write them (`backend/app/Modules/Sales/Models/Customer.php:10-14`; pinned by `backend/tests/Feature/Sales/CustomerTallyLedgerLinkTest.php:82-97`). Validation: GSTIN by the 15-character regex, `state_code` two digits (`backend/app/Modules/Sales/Http/Requests/StoreCustomerRequest.php:17-24`; `UpdateCustomerRequest.php:20-27`). The GST state code is stored as the two-digit code only; the customer screen prints the raw code (`frontend/src/features/sales/pages/CustomersPage.tsx:109`) — the same "34 not Puducherry" gap chapter 1 §2 records for vendors.

The resource prints every column plus the ledger pair (read-only), `archived_at` (soft-delete distinct from `is_active`) and a `can` block whose `delete` is undetermined on the list and answered by `show` (`backend/app/Modules/Sales/Http/Resources/CustomerResource.php:17-53`). Other documents name a customer by `{id, code, name}` only (`:62-69`).

### 1b. How customers are created and imported

**By hand.** `POST /sales/customers` under `module:sales` (`backend/routes/api.php:640-645`), `CustomerService::create` forcing `is_active` true (`backend/app/Modules/Sales/Services/CustomerService.php:23-29`). The Customers page's create and edit modals take code, name, email, phone, GSTIN and state code (`CustomersPage.tsx:11-22,176-199,213-236`); `address` is accepted by the API but has no field on either form (a small gap; the API contract is at `frontend/src/features/sales/api.ts:31-39`). The list is server-paged, clamped at 200 per page (`backend/app/Modules/Sales/Http/Controllers/CustomerController.php:30-38`; `CustomersPage.tsx:34-40,89-102`).

**From Tally ledgers — an explicit run, not a sync.** `sales:import-customers-from-ledgers {--groups=*} {--link-existing} {--write}` (`backend/app/Console/Commands/ImportCustomersFromLedgers.php:77-80`). Without `--groups` it prints a census of every Tally group in the pulled `ledgers` table and writes nothing (`:110-133,152-160`); group names are an exact allow-list and membership is never inferred from a parent group, because the owner confirmed the BUSINESS meaning of the regional groups, not Tally's tree (`:22-36`; `DEC-20260809-002`, `docs/factory/CURRENT-DECISIONS.md:156`). Each ledger becomes a customer with code `TL-{ledger id}` and NULL email, phone, address, GSTIN and state (`:67,211,241-252` — "Left NULL, never fabricated"); a soft-deleted customer is not resurrected (`:213-215`); a same-name customer from another source is reported, never merged (`:232-239`); the ledger link is written by `forceFill` and this command is its only writer (`:451-457`). The dry run does the real work inside a transaction it always rolls back (`:263-272`). `--link-existing` backfills the link on `TL-` customers that predate the columns and never overwrites a link already set (`:323-429`). Tests: `backend/tests/Feature/ImportCustomersFromLedgersTest.php:30-254`.

The manual GitHub workflow "Import customers from Tally ledgers" runs that command on the server with inputs `groups` (empty = census) and `write` (default false), never on push (`.github/workflows/import-customers-from-ledgers.yml:1-20,34-42,134-137,151`). It requires `ledgers` to have been populated by the agent's masters pull first (`ImportCustomersFromLedgers.php:119-125`).

### 1c. "Review / reconciliation with Tally"

There is no customer-side Tally review. The only Tally review tab in the ERP is the vendor one (`frontend/src/features/procurement/pages/VendorsPage.tsx`, `vendorTabs.ts`; nothing under `backend/app/Modules/Sales` or `frontend/src/features/sales` matches `tally review` / `ledger review`). The masters pull writes `ledgers` and never touches `customers` (the only references to `Customer` in `backend/app/Modules/TallySync/Services/` are the importer's match and the dormant voucher payload — §5). What the ERP does with a customer's Tally identity today is exactly two things: match an imported Sales voucher's `PARTYLEDGERNAME` to `customers.tally_ledger_name` (`backend/app/Modules/TallySync/Services/TallySalesInvoiceImporter.php:123-137`), and show "posts as {ledger}" or "no Tally ledger" on the customer row (`CustomersPage.tsx:125-131`). See "Not found".

### 1d. FC-06 and the customer

`FC-06`: purchase rates and supplier details are Owner/Accounts only; Sales sees derived money, never the bags behind it (`docs/factory/FACTORY-CONSTITUTION.md:74-82`). A customer ledger is not a supplier identity and carries no rate, so FC-06 does not reach the customer master at all (`2026_08_26_110000_add_tally_ledger_link_to_customers.php:42-43`; `CustomerResource.php:34-35`). What FC-06 hides on the SALES surface is in §6.

### 1e. Lifecycle (DEC-20260817-002)

Customer is on the Configuration Lifecycle Contract: `archive` and `activate` take a reason (`ConfigurationReasonRequest`) and mutate nothing in Tally (`CustomerController.php:71-89`; routes `backend/routes/api.php:641-645`); `destroy` is the hard delete, refused with counts when any dependency exists and refused below the Owner tier (`CustomerController.php:59-69`; authority `configuration-delete.manage`, `backend/app/Support/Configuration/HardDeleteAuthority.php:66`). The dependency list is the guard: `sales_orders`, `invoices`, `opportunities`, `quotations`, `leads.converted_customer_id` (set-null, so declared because the database would not refuse), the fail-closed "opportunity later reassigned" check that returns null — a block — whenever ANY opportunity exists, and `tally_sales_invoices.customer_id` so an imported Tally voucher can never be un-named by a delete (`CustomerService.php:43-142`). Tests: `backend/tests/Feature/Configuration/CustomerLifecycleTest.php:54-271` (archive/activate, tier refusal, counts, set-null block, real delete frees the code, reassignment refusal, archived code stays reserved). Screen: `ConfigurationActionsCell` offers Edit, Archive/Activate with a reason modal, and Delete through `DeleteConfigurationModal` (`CustomersPage.tsx:138-163`; `frontend/src/components/configuration/ConfigurationActionsCell.tsx:80-142`).

A retired customer cannot be put on a new order: `customer_id` must exist with `is_active = true` (`backend/app/Modules/Sales/Http/Requests/StoreSalesOrderRequest.php:18-19`), and the order form's picker filters to active customers (`frontend/src/features/sales/pages/SalesOrdersPage.tsx:496-500`).

## 2. Sales order

### 2a. Fields, line fields, statuses

Header: `customer_id` (restrict on delete), `status` (default `draft`), `order_date`, `expected_date` (nullable), `customer_po_reference` (nullable, free text, not unique, max 255), `notes`, `created_by` (`backend/database/migrations/2026_07_18_163622_create_sales_orders_table.php:11-20`; `2026_08_26_110001_add_customer_po_reference_to_sales_orders.php:17-28,35`; `backend/app/Modules/Sales/Models/SalesOrder.php:19`). Line: `item_id`, `quantity` decimal(15,4), `unit_price` decimal(15,4), `quantity_delivered` default 0 (`2026_07_18_163623_create_sales_order_lines_table.php:11-19`), plus the four dispatch-approval columns (§4a). There is NO unit column on the line: the unit is the item master's `uom`, printed through `ItemResource` (`backend/app/Modules/Sales/Http/Resources/SalesOrderLineResource.php:13-19`; `backend/app/Modules/Inventory/Http/Resources/ItemResource.php`). There is no "promised date" column — the field is `expected_date`, labelled "Expected Date" on the form, the resource and the drawer, validated only as `after_or_equal:order_date`; whether it is a promise to the customer "has never been recorded" (`Q67`, `docs/factory/PENDING-OWNER-QUESTIONS.md:1808-1880`; `StoreSalesOrderRequest.php:21`; `frontend/src/features/sales/SalesDocumentDrawer.tsx:242`). The records from 02-Sep say "promised date" (`DEC-20260902-031`, `DEC-20260902-033`); see Conflicts.

Exact status strings: `draft`, `confirmed`, `partially_delivered`, `completed`, `cancelled` (`backend/app/Modules/Sales/Models/Enums/SalesOrderStatus.php:5-12`; frontend union `frontend/src/features/sales/types.ts:36`). Transitions: create → `draft` (`backend/app/Modules/Sales/Services/SalesOrderService.php:120-147`); `confirm` from `draft` only (`:149-162`); `cancel` from `draft` or `confirmed` with every line's `quantity_delivered` zero and NO invoice, drafts included (`SalesOrder::isCancellable`, `SalesOrder.php:176-194`; `SalesOrderService.php:187-225`); a delivery moves the order to `completed` when every line is fully delivered, else `partially_delivered` when anything has (`backend/app/Modules/Sales/Services/DeliveryService.php:401-420`). A cancel gives up every live hold with reason `so_cancelled` and withdraws every open production request, under the order-row lock, and moves no stock (`SalesOrderService.php:177-222`; `backend/tests/Feature/Sales/SalesOrderCancelReleasesFulfilmentTest.php:60-118`). Cancel records neither who nor why — `Q44(d)`.

The document number is `SO-{id}` (`SalesOrder.php:123-127`).

### 2b. Who may create, confirm, cancel — and there is no amend

Routes: `sales-orders` index/store/show, `confirm`, `cancel`, `cost-insight`, all under `Route::prefix('sales')->middleware('module:sales')` (`backend/routes/api.php:679-690`). `EnsureModulePermission` requires `sales.view` for a GET and `sales.manage` for any other verb (`backend/app/Http/Middleware/EnsureModulePermission.php:31-52`), pinned for cancel by `backend/tests/Feature/Sales/SalesOrderCancelTest.php:292`. There is no `update`/`amend` route and no `SalesOrderService::update` method; the only changes an order can undergo after creation are confirm, cancel and the delivery-driven status moves. Chapter 3's OPEN 3 (amendment after a hold exists) therefore asks about something that does not exist in any form today.

Permission names are `sales.view` / `sales.manage` from the module catalogue (`backend/app/Modules/Core/Services/PermissionService.php:81`). No "Sales" ROLE is seeded anywhere: `PermissionSeeder` creates Administrator (everything), Plant Manager and Accounts (`backend/database/seeders/PermissionSeeder.php:29-30,46-47,66-67`); the acceptance fixture seeds Plant Manager and Accounts plus a Supervisor login (`backend/database/seeders/AcceptanceFixtureSeeder.php:219-222`); the Storekeeper role definition grants `inventory.view`, `inventory.manage`, `production.view`, `quality.view` and refuses `finance.view` under FC-06 (`backend/app/Console/Commands/DefineStorekeeperRole.php:82-98,155-158`). Which live logins hold `sales.manage` was not read.

### 2c. What the picker offers today

The order form's item picker calls `listAllItems`, which is `GET /inventory/items?per_page=1000` (`SalesOrdersPage.tsx:9,494`; `frontend/src/features/inventory/api.ts:59-63`), and maps EVERY returned row into an option with no `is_active` and no `category` filter (`SalesOrdersPage.tsx:506`); the server's list applies no filter either (`backend/app/Modules/Inventory/Services/ItemService.php:223-233`). The request validates `lines.*.item_id` as `exists:items,id` only (`StoreSalesOrderRequest.php:30`). So a raw material, a packing material, scrap, an unclassified item and an INACTIVE item can all be put on a sales order today — `DEC-20260902-035` (active Finished Good only, refused server-side) is recorded and not built, on both halves, as chapter 2 §14 and the Opus review §4.2(f) already say. The rollout trap the review names stands: on unclassified live items the refusal would refuse every order on day one (`docs/factory/workflows/research/2026-09-02-opus-review-of-decisions.md:391-401`).

Beside each line the form shows availability chips — `on_hand`, `reserved`, `free`, `over_reserved` for the finished-goods store — from `GET /sales/availability?item_ids[]=`, one request for all lines, capped at 200 items, four keys and no cost (`SalesOrdersPage.tsx:527-533,752-758`; `backend/app/Modules/Sales/Http/Controllers/SalesAvailabilityController.php:11-38`; `backend/app/Modules/Inventory/Services/AvailabilityService.php:46-103`; `backend/app/Modules/Sales/Http/Resources/ItemAvailabilityResource.php:8-40`). Seeing free stock holds nothing (`SalesAvailabilityController.php:21-25`).

### 2d. What "lock order" means in code

Not a business "locking" of an order. It is the GLOBAL ROW-LOCK ORDER every multi-lock path in the fulfilment build takes: `sales_orders / sales_order_lines → material_bags → stock_balances → stock_reservations → production_requests` (`backend/app/Modules/Inventory/Services/StockReservationService.php:30-49`). reserve, repoint and send-to-production lock the parent order row first and re-judge its status under that lock (`:182-190,256-260`; `backend/app/Modules/Production/Services/ProductionRequestService.php:162-176`); a dispatch takes the same order-then-lines locks at its head (`DeliveryService.php:129-137,343-352`); cancel holds the order row while it releases holds and withdraws requests (`SalesOrderService.php:189-219`); `markProducedIfCovered` deliberately locks nothing above `production_requests` (`ProductionRequestService.php:35-38,363-366`). The balance lock in the hold path is read-only and taken by hand, never through `StockMovementService::lockBalance()`, so asking whether stock is free can never create a balance row (`StockReservationService.php:51-57,514-521`).

### 2e. How an order's status is updated from a Tally invoice match

It is not. A match writes `tally_sales_invoices.sales_order_id` and `customer_id` on the imported row (§5); the order answers `isInvoicedInTally()` as a DERIVED read — "does a matched Tally voucher exist right now" — and the model states it "does not touch `status`": the lifecycle is driven by what the factory did (delivery), and "whether a Tally invoice should also CLOSE an order is a business rule nobody has stated, so it is not invented here" (`SalesOrder.php:83-116`). The API exposes a `tally_invoice` block — `invoiced_in_tally` plus matched vouchers' number, date and amount — BESIDE `status`, never folded into it (`backend/app/Modules/Sales/Http/Resources/SalesOrderResource.php:45-54,104-126`); the importer never writes `sales_orders.status` (its only `status` reference excludes cancelled orders from matching, `TallySalesInvoiceImporter.php:144`). No frontend file reads `tally_invoice` or `invoiced_in_tally` (grep of `frontend/src` returns nothing) and the `SalesOrder` type declares no such key (`frontend/src/features/sales/types.ts:60-90`). The rehearsal asserts the block on the API only (`backend/tests/Feature/Acceptance/SalesFulfilmentRehearsalTest.php:290-301`). See Conflicts, 1.

## 3. Stock hold and fulfilment

### 3a. The Store Fulfilment queue

One row per line of every `confirmed` or `partially_delivered` order (`backend/app/Modules/Inventory/Services/FulfilmentQueueService.php:169-179`), with the line's `ordered / delivered / reserved / shortfall`, the ITEM's `free / over_reserved` in the finished-goods store, a `fulfilment_state`, the live holds ("held for {customer} since {date}", oldest first, with each hold's `outstanding_quantity`), the open production request if any, and `can {reserve, release, repoint, send_to_production}` computed from the same predicates the writes refuse on (`:224-280,341-352,366-387`). States: `untouched`, `partially_allocated`, `awaiting_production`, `over_reserved`, `fully_allocated` (`:53-75`, asked in the order `:297-320`). Over-reserved rows sort first across the whole queue; `fully_allocated` rows are hidden unless `?state=fully_allocated` is asked for by name; paging is 25 by default, 200 max, done in PHP (`:30-45,95-115,207-215`; `backend/app/Modules/Inventory/Http/Requests/ListFulfilmentQueueRequest.php:33-37`). No rate, no cost, no supplier: the line's `unit_price` is deliberately not read (`:47-49`; `backend/app/Modules/Inventory/Http/Resources/FulfilmentQueueRowResource.php:32-34`; pinned by `backend/tests/Feature/Inventory/FulfilmentQueueEndpointTest.php:289`). The page keeps state and page in the URL and offers Release / Re-point on each hold row and Hold / Send to production on the line (`frontend/src/features/inventory/pages/StoreFulfilmentPage.tsx:52-63,68-105,115-139,172-250`).

The finished-goods warehouse every hold is taken against is the app setting `production_finished_goods_warehouse_id`, resolved `OrFail` so an unconfigured store refuses rather than reading as empty (`StockReservationService.php:157-166`; `backend/app/Modules/Production/Services/FactoryWarehouseResolver.php:65,262`; `FulfilmentQueueEndpointTest.php:244`). Its live value was not read.

### 3b. Placing a hold, and the three refusals

`POST /inventory/fulfilment/lines/{line}/reserve {quantity}` (`backend/app/Modules/Inventory/Http/Requests/ReserveStockRequest.php:32-37`) → `StockReservationService::reserve` (`:177-208`): lock the order row and refuse unless it is `confirmed` or `partially_delivered` (`:580-595`); lock the line; lock the balance row read-only (an absent row is zero, never created, `:428-430,514-521`); then refuse when nothing is free (`nothingFree`, `:434-440`), when the asked quantity exceeds free = on-hand − active holds (`notEnoughFree`, `:442-448`), or when it exceeds what the line still owes = ordered − delivered − already held (the demand cap, `:450-464`); else insert an `active` `stock_reservations` row (`:466-475`). Every refusal quotes the real figure (`backend/app/Modules/Inventory/Exceptions/StockReservationException.php:15-21,39-68`). No stock movement is written by any method of the class (`:23-28`; `backend/database/migrations/2026_08_26_100000_create_stock_reservations_table.php:11-15`; `backend/tests/Feature/Inventory/FulfilmentActionsEndpointTest.php:61-95`). A hold taken on a line the store just covered also retires that line's QUEUED production request (`:199-204`).

### 3c. Releasing

`POST /inventory/reservations/{id}/release {reason}` — reason required, 3–255 characters (`backend/app/Modules/Inventory/Http/Requests/ReleaseReservationRequest.php:28-40`) → gives up the hold's outstanding quantity, stamping `released_quantity`, `released_reason`, `released_by` and re-deriving `status` (`StockReservationService.php:219-232,479-507`). A fully consumed hold refuses ("Stock that left on a delivery is corrected by a delivery, never by giving up the hold", `StockReservationException.php:82-88`). A hold is never edited or deleted; it keeps its row (`create_stock_reservations_table.php:17-21`). Statuses: `active`, `released`, `consumed`, maintained from the three quantities (`backend/app/Modules/Inventory/Models/Enums/StockReservationStatus.php:22-38`).

### 3d. Re-pointing, with a reason

`POST /inventory/reservations/{id}/repoint {sales_order_line_id, quantity, reason}` (`backend/app/Modules/Inventory/Http/Requests/RepointReservationRequest.php:33-40`) → `StockReservationService::repoint` (`:246-311`): lock the TARGET's order and line; keep the SOURCE hold's warehouse (a hold moves between lines, never between warehouses, `:262-272`); refuse a spent source, a same-line target, an item mismatch, or more than the source still holds (`:279-298`); release the source FIRST and then take the new hold under the same balance lock, so the pieces in flight count as free (`:237-244,300-302`); retire the target's queued request if now covered (`:304-307`). Source line, target line, quantity, reason and person are on the two rows (`released_reason`, `released_by`, `created_by`). This is the shipped behaviour `DEC-20260902-028` and `DEC-20260902-029` confirm (first hold wins; the Store re-points on its own judgement; no approval step; `DEC-20260902-040` restates both). Test: `FulfilmentActionsEndpointTest.php:205-249`.

### 3e. Sending the shortage to Production

`POST /inventory/fulfilment/lines/{line}/send-to-production {quantity}` (`backend/app/Modules/Inventory/Http/Requests/SendToProductionRequest.php:27-32`) → `ProductionRequestService::createFromShortfall` (`ProductionRequestService.php:157-216`): lock the order (must be live) and the line; read the held figure under the reservation locks; refuse if an OPEN request already stands on the line (`alreadyOpenForLine`, `:185-193`); compute shortfall = ordered − delivered − held and refuse if nothing is short (`:195-203`); CAP the typed quantity at the shortfall rather than refusing (`:205`); insert a `queued` `production_requests` row at priority max + 1 (`:207-214,422-427`). The request is paperwork: no batch is created, started or cancelled, no FK into `shift_production_entries` (`backend/database/migrations/2026_08_26_100001_create_production_requests_table.php:11-16`; `backend/app/Modules/Production/Models/ProductionRequest.php:14-28`). Statuses `queued`, `in_progress`, `produced`, `cancelled` (`backend/app/Modules/Production/Models/Enums/ProductionRequestStatus.php:30-50`). Document number `PR-{id}` (`ProductionRequest.php:55-58`).

### 3f. How "covered" is computed (DEC-20260902-032)

Coverage = the line's `quantity_delivered` + the OUTSTANDING quantity of its active holds (quantity − consumed − released), read under the reservation locks; when coverage ≥ ordered, the line's `queued` requests flip to `produced`; an `in_progress` request is never retired by this path (`ProductionRequestService.php:336-398`, especially `:382-391`; `backend/app/Modules/Inventory/Models/StockReservation.php:84-100`). The consumed part of a hold is not counted twice, because it already is the delivered pieces (`:339-353`). The same fold drives the order's "Ready for dispatch" badge (`FulfilmentQueueService::readyForDispatch`, `:117-159`; `backend/tests/Feature/Sales/ReadyForDispatchBadgeTest.php:60-146`) and the control board's `held` (`backend/app/Modules/Sales/Services/FulfilmentControlService.php:388-407`). `DEC-20260902-032` records exactly this formula as the rule ("confirms the shipped formula").

### 3g. How the production queue is ordered today (DEC-20260902-031 is not built)

`GET /production/requests` and the planning walk read open requests `orderBy('priority')->orderBy('id')` (`ProductionRequestService.php:57-64`; `backend/app/Modules/Production/Services/FulfilmentPlanningService.php:109-119`). `priority` is dense and 1-based, set to max + 1 at creation — raised order — and rewritten wholesale by `POST /production/requests/reorder {ordered_ids}`, which must name every open request and takes NO reason (`ProductionRequestService.php:231-263`; `backend/app/Modules/Production/Http/Requests/ReorderProductionRequestsRequest.php:27-31`). The `production_requests` table carries `sales_order_line_id, item_id, quantity, priority, status, requested_by, cancelled_reason` and nothing else (`create_production_requests_table.php:44-82`); no `promised_date` sort, no manual-position marker, no reorder reason and no "moved since Production last looked" flag exists anywhere (grep of `backend/app`, `backend/database`, `frontend/src` for `promised_date`, `manual_position`, `reorder_reason`, `moved_since`: nothing). The queue screen's row shows the order's `expected_date` only to a login holding `sales.view/manage`, and the planning block only to `inventory.view/manage` (`backend/app/Modules/Production/Http/Resources/ProductionQueueResource.php:64-107`; `Q67`). The planning read stays one machine per product (`config('production.planning.parallel_lines', 1)`, `FulfilmentPlanningService.php:89-94`) and prints its basis in the payload, which is the GAP chapter 2 §14 records against `DEC-20260902-033`.

### 3h. What the Sales and Store dashboards show about orders today

`DashboardService::summary` gives a login holding `sales.view/manage` a `sales` block — `open_sales_orders` (confirmed + partially delivered, `SalesOrderService.php:93-98`), `orders_awaiting_delivery` (the SAME predicate, `DeliveryService::pendingCount`, `DeliveryService.php:111-121`) and `receivables_outstanding` (a money total over the ERP's OWN unpaid invoices, `backend/app/Modules/Finance/Services/AccountsReceivableService.php:46-53`) — plus a `demand` order book (every undelivered open line with on-hand across all warehouses, the shortfall to produce, and hours at the standard rate where exactly one usable standard exists) and the five most recent orders (`backend/app/Modules/Core/Services/DashboardService.php:83-91,141-210,233-245`). The page renders them as the "Order book · open orders against the shelf" table, three tiles and a recent-orders table (`frontend/src/features/dashboard/pages/DashboardPage.tsx:415-460,532-546,605-620`). Nothing on the dashboard counts held stock, lines awaiting Quality, lines ready to dispatch, or Tally invoices matched — the four things the Sales row of the role-dashboard table asks for; and the `inventory` block a Store login sees is `total_items`, `total_warehouses`, `low_stock_items` only (`DashboardService.php:63-69`) — nothing about holds or dispatch. The `demand` block's `on_hand` is `totalOnHand` across every warehouse, not the finished-goods store, and does not subtract holds (`:168`), so it can disagree with the fulfilment queue's `free`.

The shared picture lives instead on the Fulfilment Control board: one row per live line with `ordered / delivered / invoiced / available_stock / held / over_reserved / shortfall / stock_held / dispatch_ready`, the store, production and quality blocks, and a `blocker` naming who acts next — codes `over_reserved` (Store, severity 8), `short_and_not_requested` (Store, 7), `store_has_not_held_stock` (Store, 6), `queued_for_production` (Production, 4), `in_production` (Production, 3), `awaiting_quality_approval` (Quality, 3), `awaiting_invoice` (Accounts, 2), `ready_to_dispatch` (Store, 1), `complete` (0) — sorted trouble first (`FulfilmentControlService.php:72-121,128-243,253-352`). `store.rejected`, `production.planned` and `production.completed` are the string `not_recorded` with a sentence each, because no source exists (`:31-49,204-223`; `Q73`). The board is read-only for everyone and carries Quality's approve/revoke as its one act (`FulfilmentControlPage.tsx:22-25,84-118`). `hours_at_standard` on the dashboard and the planning ETA are two different estimates from two different services; nothing reconciles them.

## 4. Quality approval before dispatch, and the dispatch act

### 4a. "Internal Quality approval" in code

Four nullable columns on `sales_order_lines`: `quality_approved_at`, `quality_approved_by` (user, null on delete), `quality_approved_quantity`, `quality_approval_note` (`backend/database/migrations/2026_08_31_010000_add_dispatch_quality_approval_to_sales_order_lines.php:29-35`). The timestamp is the fact; the quantity is what caps dispatch (`backend/app/Modules/Sales/Models/SalesOrderLine.php:25-41`).

`POST /quality/dispatch-approvals/lines/{line}/approve {note?}` — inside the `module:quality` group, so `quality.manage`; Sales cannot sign off its own dispatch and a `quality.view`-only login is refused (`backend/routes/api.php:768,822-828`; `backend/tests/Feature/Sales/DispatchQualityGateTest.php:101-119`). `DispatchQualityApprovalService::approve` (`backend/app/Modules/Sales/Services/DispatchQualityApprovalService.php:44-80`): lock the line; refuse unless the order is `confirmed` or `partially_delivered`; refuse a second approval in place (withdraw first); read the held figure under the reservation locks and REFUSE unless held ≥ outstanding — "fully held is the owner's precondition" (`:64-69`; `DEC-20260831-006`); stamp who, when, the held quantity and the note. `revoke` clears the four columns and is refused once `quantity_delivered > 0` — "history is not rewritten; raise a non-conformance report instead" (`:83-105`; `backend/app/Modules/Sales/Exceptions/DispatchQualityException.php:36-42`). The response and the control board print who, when, how much, the note and `dispatchable` = approved − delivered, never a rate (`backend/app/Modules/Sales/Http/Controllers/DispatchQualityApprovalController.php:41-60`; `FulfilmentControlService.php:225-238`).

It cannot be skipped: `DeliveryService::create` refuses every line that has no approval and every quantity beyond the approved remainder, inside the same transaction and line lock as the over-delivery cap, with no configuration switch around it (`DeliveryService.php:174-196`; `backend/app/Modules/Sales/Exceptions/DispatchNotQualityApprovedException.php:17-31`; `DispatchQualityGateTest.php:121-147`).

**What it does NOT check.** The service reads the order, the line and the holds — nothing about a production batch, a shift entry, a carton or the finished-goods quality check (grep of `DispatchQualityApprovalService.php` for `ShiftProductionEntry|batch|quality_checked|carton`: nothing). A hold is a quantity in a warehouse (`stock_reservations` has `item_id, warehouse_id, sales_order_line_id`, no batch and no carton, `create_stock_reservations_table.php:51-59`), so nothing joins the approved pieces to the batch that made them. The only batch-quality gate on the dispatch path is the carton scan's refusal of a carton whose batch is `rejected`; a carton of a batch "merely NOT YET through QC/approval" passes, as the code says in so many words (`DeliveryService.php:372-381`; `DEC-20260807-013`; `backend/tests/Feature/Sales/DispatchRefusesQualityRejectedCartonTest.php:187-264`), and a TYPED delivery has no batch check at all (`:163-233`). `DEC-20260831-006` records Q27 as resolved by "option (b), the QC pass required"; what was built is a line-level internal sign-off of a HELD QUANTITY, not a check that the batch passed its quality stage. See Conflicts, 5 and 6.

### 4b. Raising a delivery — the Store dispatches (DEC-20260901-005)

`POST /sales/deliveries` sits in its own `module:inventory` group, so `inventory.manage` dispatches and `sales.manage` gets 403; index and show are OR-gated `sales,inventory` so the desk that sold the goods still traces what left (`backend/routes/api.php:697-725`). Pinned both ways, including that a dispatching Store login gains no access to orders, customers or invoices (`DispatchQualityGateTest.php:178-207`; `SalesFulfilmentRehearsalTest.php:127-141`). The Deliveries page hides "New Delivery" unless the user holds `inventory.manage` (`frontend/src/features/sales/pages/DeliveriesPage.tsx:40-47,183`; `frontend/src/features/auth/permissions.ts:8-11`). The route comment names the decision as `DEC-20260901-001`, the id it was first minted under (`:699`; see Conflicts, 3).

### 4c. What a delivery records

`deliveries`: `sales_order_id`, `warehouse_id` (any existing warehouse — the form offers `listAllWarehouses`), `reference`, `delivered_date` (datetime, defaults to now), `notes`, `created_by` (`backend/database/migrations/2026_07_18_163624_create_deliveries_table.php:11-20`; `backend/app/Modules/Sales/Http/Requests/StoreDeliveryRequest.php:17-22`; `DeliveriesPage.tsx:65,72`). `delivery_lines`: `sales_order_line_id`, `item_id`, `quantity` (`2026_07_18_163625_create_delivery_lines_table.php:11-18`). Number `DN-{id}` (`backend/app/Modules/Sales/Models/Delivery.php:62-66`).

Two input shapes, never both: typed `lines[{sales_order_line_id, quantity}]`, or `carton_codes[]` from which the lines are DERIVED (`StoreDeliveryRequest.php:23-34`; `DeliveryService.php:152-161,354-399`). A scanned carton must exist, be `in_stock`, belong to a batch that is not `rejected`, and carry an item on this order; it is locked, stamped `dispatched` and tied to the delivery (`:359-392`; `backend/database/migrations/2026_08_02_210001_create_finished_cartons_table.php:18-32`). The page resolves each scan through `GET /production/cartons/{cartonNo}` — a `module:production` route, so the scanner needs `production.view`, which the Storekeeper role carries (`DeliveriesPage.tsx:82-117`; `backend/routes/api.php:994,1040`; `DefineStorekeeperRole.php:94`). The rehearsal itself dispatches by typed lines "because the live instance has no cartons at all" (`SalesFulfilmentRehearsalTest.php:118-120`) — see "Not found". The Deliveries list shows Number, SO, Customer, Warehouse, Delivered, Reference, Lines, Cartons and a Tally column for the Delivery Note's sync state (`DeliveriesPage.tsx:210-249`); the show trace carries the order, the cartons with their batch number, and the Tally link — no lot, no rate (`backend/app/Modules/Sales/Services/SalesDocumentTraceService.php:119-135,212-228`).

### 4d. What stock movement it makes, and from where

Per line, inside one transaction: refuse above the ordered remainder (`OverDeliveryException`, `DeliveryService.php:169-172`); the Quality gate (`:185-196`); create the delivery line; `StockMovementService::recordIssue` for the line's item, the delivery's `warehouse_id`, purpose `dispatch` (`:204-213`; `backend/app/Modules/Inventory/Models/Enums/StockMovementPurpose.php:55-56`); increment `quantity_delivered` (`:215`); spend holds (`:228-232`); recompute the order status (`:235`); fire `DeliveryDispatched` (`:240`). One issue movement per line, asserted on the ledger (`SalesFulfilmentRehearsalTest.php:143-151`). The incoming-QC hold on the balance applies to this door like every other (research note §2b of the chapter 2 note; `backend/app/Modules/Inventory/Services/StockMovementService.php:915-926`).

Holds are spent ONLY from holds whose `warehouse_id` equals the delivery's, oldest first; a delivery from another warehouse spends no hold and is not an error, because the holds sit in the FG store and "the van may legally have loaded elsewhere" (`StockReservationService.php:313-341`; `backend/tests/Feature/Sales/DeliverySpendsTheHoldTest.php:74-146`). When the line is then fully delivered, its leftover holds are released with reason `line_fulfilled` and its queued request flips to `produced` (`:364-384`). Under `DEC-20260830-002` (one operational Store) a dispatch from a warehouse other than the FG store leaves the hold standing; the form does not prevent it.

### 4e. Partial deliveries

Allowed. A line may be delivered in any quantity ≤ its ordered remainder and ≤ its approved remainder; the order becomes `partially_delivered` and the rest stays on the queue (`DeliveryService.php:169-196,401-420`). Quality's approval must be of a FULLY HELD line (§4a), so a partial dispatch of an approved line is a dispatch of part of the held-and-approved quantity, never of a line still short. Chapter 3's OPEN 1 asks whether that should stay so; no record answers it.

### 4f. What a delivery can and cannot do after it is recorded

Nothing. The `deliveries` resource is `index`, `show`, `store` only (`backend/routes/api.php:719-725`); `Delivery` has no status column ("a Delivery row only ever represents stock that has already gone out", `DeliveryService.php:111-115`); no cancel, amend or reverse method exists in `DeliveryService`; a consumed hold cannot be released ("corrected by a delivery, never by giving up the hold", `StockReservationException.php:82-88`); and a Quality approval cannot be withdrawn after anything shipped (§4a). `DEC-20260901-005` leaves "whether the Store may also CANCEL or reverse a dispatch it made" expressly undecided, and nothing was built. The dispatch event still reaches TallySync's listener, which no-ops while `delivery_notes_enabled` is off (§5e).

## 5. Tally Sales Invoice import and match

### 5a. How the XML gets in

`php artisan tally:import-sales-invoices {path} {--write}` reads a Tally XML export from a file path (UTF-16 or UTF-8), prints a verdict table and is a DRY RUN unless `--write` is given (`backend/app/Console/Commands/ImportTallySalesInvoices.php:9-67`; `backend/tests/Feature/TallySync/TallySalesInvoiceImportTest.php:300-317`). There is no HTTP route, no upload, no agent path and no GitHub workflow for it (grep of `backend/routes`, `frontend/src`, `.github/workflows`, `scripts/` for `sales-invoice`/`import-sales-invoices`: nothing) — the agent's only inbound reads are masters, purchase rates, receivables and the stock-summary preview (`backend/routes/api.php:900-925`). The importer reads vouchers of type `Sales` only and ignores `Sales Order` vouchers (`backend/app/Modules/TallySync/Services/TallySalesInvoiceImporter.php:45-46,59-61`; test `:98`).

### 5b. The matching key (DEC-20260831-012)

Per voucher: `GUID`, `VOUCHERNUMBER`, `PARTYLEDGERNAME`, the order reference from `BASICPURCHASEORDERNO` else `REFERENCE` (never `ORDERNO`, which Tally fills with "Not Applicable"), the date and the party line's amount (`TallySalesInvoiceImporter.php:97-113,199-255`). Direct child tags only, so an e-way bill's copy of the reference is never read as the voucher's (`:264-279`). Customer = the ERP customer whose `tally_ledger_name` equals the party — the link the import command wrote, never a name match (`:123-137`). Order = the customer's non-cancelled orders whose `customer_po_reference` equals the string exactly (`:141-145`; long free-text references match as typed, test `:137`). Verdicts: `matched`, `unmatched_no_reference`, `unmatched_no_customer`, `unmatched_no_order`, `ambiguous` (`backend/app/Modules/TallySync/Models/Enums/TallyInvoiceMatchState.php:13-28`). The evidence the key rests on is the factory's 31-Aug export (`DEC-20260831-012`; fixture `backend/tests/fixtures/tally/sales-invoices.xml`, manifest `docs/factory/sources/manifest.json:151-165`).

### 5c. What happens to an unmatched invoice

It is written to `tally_sales_invoices` with `match_state`, a `match_detail` sentence naming the missing thing, `customer_id` where the customer resolved, and `sales_order_id` null; two candidate orders are `ambiguous`, refused rather than picked; no customer and no order is ever created (`:33-37,115-166`; migration `backend/database/migrations/2026_08_31_120000_create_tally_sales_invoices_table.php:24-48`; tests `:163-236`). Re-import is a no-op keyed on `tally_guid`, and a late order makes a previously unmatched voucher match on the next import (`:191-197`; tests `:268-298`). Who resolves an unmatched row, and where they see it, is not built: no route or page lists `tally_sales_invoices` (grep: nothing) — the command's console table is the only view. `DEC-20260831-012` says it "is recorded as unmatched for a person to resolve"; Chapter 3's OPEN 5 asks who and how.

### 5d. What the ERP updates on a match

The `tally_sales_invoices` row's `sales_order_id` and `customer_id`. Nothing on `sales_orders` (§2e). The order's API payload gains `tally_invoice.invoiced_in_tally = true` and the matched vouchers' number, date and amount (`SalesOrderResource.php:112-126`); the customer's hard delete is thereafter blocked by the imported voucher (`CustomerService.php:133-140`). ## 6. Pricing and money

**What a line carries and where it comes from.** `unit_price` decimal(15,4), required, `min:0`, typed by the sales desk on the order form (`create_sales_order_lines_table.php:16`; `StoreSalesOrderRequest.php:32`; `SalesOrdersPage.tsx:747`). No price list, price master or last-price lookup exists (grep of `backend/app`, `backend/database`, `frontend/src` for `price_list|PriceList|selling_price|list_price`: nothing). The ERP invoice line carries its own typed `unit_price` again (`backend/app/Modules/Sales/Http/Requests/StoreInvoiceRequest.php:30`). The Tally invoice's `amount` is imported as the party line's total, never derived (`TallySalesInvoiceImporter.php:222-255`).

**Who sees the selling price.** Anyone with `sales.view` — the order resource prints `unit_price` on every line (`SalesOrderLineResource.php:17`) and the drawer shows `quantity × price` (`SalesOrdersPage.tsx:280`). Every Store, floor and Quality surface omits it by design: the fulfilment queue (`FulfilmentQueueRowResource.php:32-34`), the control board (`backend/app/Modules/Sales/Http/Resources/FulfilmentControlRowResource.php:33-34`), the production request and queue rows (`backend/app/Modules/Production/Http/Resources/ProductionRequestResource.php:29-30`; `ProductionQueueResource.php:53-55`), the Quality sign-off payload (`DispatchQualityApprovalController.php:41-44`), every hold (`create_stock_reservations_table.php:33-34`; `FulfilmentActionsEndpointTest.php:350`). The delivery/invoice traces keep the selling price ("the customer's") and never a purchase rate, supplier, bag or lot (`SalesDocumentTraceService.php:33-37,212-228`).

**Cost and margin shown to Sales (FC-06).** `GET /sales/sales-orders/{id}/cost-insight`, `module:sales`, read-only (`backend/routes/api.php:688-690`; `backend/app/Modules/Sales/Http/Controllers/SalesCostInsightController.php:9-22`). Per line it returns an ESTIMATE (per-piece cost from the product's standards priced at the common resin pool's weighted average, else the moving average, labelled) and an ACTUAL (from the latest approved batch carrying a live allocation run, else null with a reason), each with a margin against `unit_price`, plus an order block with `revenue_total` and `margin_pct` (`backend/app/Modules/Sales/Services/SalesCostInsightService.php:23-118,204-260,814-919`). The per-component anatomy — per-kg rates, bag barcodes, supplier lots — rides only for `finance.view/manage`; the `components` key is ABSENT for everyone else, while identity-free `sources` sentences are present for all (`:106-118,341-342`; `backend/app/Modules/Sales/Http/Resources/SalesCostInsightResource.php:9-38`). This is the exact reading of `FC-06` ("Sales sees derived money; never the bags behind it") and its named pin `SalesCostInsightTest::test_a_sales_login_sees_the_money_but_never_the_bags_behind_it` exists (`backend/tests/Feature/SalesCostInsightTest.php:440,485,502`). The drawer renders the cost & margin section per order (`SalesOrdersPage.tsx:135-280,415-434`). So a Sales login sees a derived unit cost and a margin percentage; it never sees a purchase rate or a supplier. A dashboard money figure a `sales.view` holder also sees is `receivables_outstanding`, summed over ERP invoices (§3h); the Tally-mirrored client outstanding is a separate `module:finance` read (`backend/routes/api.php:736-760`).

## Conflicts

1. **`DEC-20260831-012` vs the code on "status".** The record: the ERP's job is to "IMPORT … MATCH … and UPDATE the ERP Sales Order's status from that match." The code writes no order status on a match, states that it will not, and exposes a derived `tally_invoice` block instead that no screen renders (`SalesOrder.php:98-116`; `SalesOrderResource.php:45-54`; §2e).
